# QQ 专属红包自动排队：当前可行性调查

调查日期：2026-09-26。以下为先前的自动识别调查。当前开发范围已调整为仅使用官方公共机器人，并采用观众申报、主播核对实际收款的流程，见 [红包核对指南](QQ-RED-PACKET.zh-CN.md)。非官方接收端不在当前实施范围内。

## 当前结论

目前没有在官方 QQ 机器人的消息接口、已安装适配器或本机事件中找到可验证的原生 QQ 红包交易金额、指定接收人和到账记录。不能把红包提示文字、标题或普通 JSON 消息当作付款凭证。现有公共机器人继续承担文字排队、UID 验证、查询和叫号；红包自动计费尚未实现。

腾讯云 IM 的红包方案是开发者自行实现红包系统，再用 IM 自定义消息传输 packet_id；它不能直接读取普通 QQ 群里的原生红包。

## 候选一：主播电脑上的个人 QQ 接收端

维护者文档中找到萌卡 NT 的 `get_red_packet_info`：接收 `red_packet` 消息段，输入群号、发送者 QQ 号、listid、authkey、pay_flag、hb_from，返回红包服务解密后的数据。示例包含 send_uin、send_listid、total_amount、total_num、recv_amount、recv_num。文档还提供领取接口，但本次没有安装框架、登录任何 QQ 账号或领取红包。

这是非官方个人 QQ 协议接入，需要登录个人 QQ 账号，不能使用当前公共机器人的 AppID / AppSecret 替代。是否支持稳定获取专属接收人、实际到账金额、退款/撤回状态以及金额单位，仍需真实小额红包验证。示例 total_amount 是整个红包金额，不等于主播实际收到的钱；total_num=1 也不证明红包指定给主播。

若测试证实可用，接收端应在主播电脑运行，金融鉴权串和登录信息不上传公共服务。必须先用验证码验证“个人 QQ 号 → B站 UID”，不能通过群昵称猜测发送者，也不能假定 QQ 号可换算成官方成员 OpenID。

入账条件必须全部满足：

- 来自主播配置的群，且指定接收人是主播。
- 已有可核验的支付/到账状态及准确金额单位；金额用整数分保存。
- 付款 QQ 身份已验证关联到 B站 UID。
- 使用群号、红包交易 ID 和接收人组合去重，同一交易不会重复累加。
- 不完整、失败、未支付、错误接收人、多人随机红包等事件不自动入账。

收到符合条件的交易后，以 B站 UID 合并队列、累计金额、保留首次等待时间并使用该房间自动同步的舰队优先级。此候选尚不能作为已实现功能发布。没有验证接口之前，不添加一个看似可用的“红包自动排队”开关。

## 候选二：独立支付链接

观众通过带订单 ID 和已验证身份的支付页面付款，服务验证支付平台签名回调或主动查询订单后入账。能够设计金额、接收人和去重机制，但需要合法可用的支付商户接口及结算安排，属于另一个支付流程，并不是 QQ 原生专属红包。当前没有配置商户，也没有创建付款入口。

## 本次验证与下一步

本次只研究公开文档，未把任何红包金额写进真实队列。建议先确认候选一的接收端是否能在测试群 168426621 提供“实际收款、指定给主播、发送者和唯一交易 ID”四项完整数据，再决定是否接入；需要用户选择接收端并授权登录后才能进行原生红包实测。
